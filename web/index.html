How it works

Three design decisions carry this whole thing. Each one is a constraint of HydraDB 0.1.0 turned into the reason the answer arrives in one traversal.

why a graph, not a vector

"Which packages are similar to event-stream" is a vector question. Nobody asks it during an incident.

The real question is reachability: who pulls this, and who pulls them, five levels down. That is a transitive closure over a directed graph — the one shape an embedding index cannot answer at all.

HydraDB answers it as one traversal from one known vertex. We also built the same closure as a recursive CTE over the SQLite sidecar and timed both. At this graph size SQLite is 3–13× faster, and both engines return the identical count on every row. BENCHMARKS.md has the table, including the row that says a 27k-vertex graph does not need a graph database.

why-a-graph.md
the reversed edge

Edges are stored backwards on purpose:

(dependency)-[:REQUIRED_BY]->(dependent)

HydraDB 0.1.0 will only run a variable-length MATCH when the source id is fixed. In an incident, the one thing you know for certain is which package was compromised.

Reversing the edge at write time makes that package the source, so the blast radius is one traversal from a known id instead of a scan of the graph.

reversed-edges.md
two stores, two shapes

HydraDB 0.1.0 cannot filter on edge properties mid-traversal, so a declared semver range cannot live on the edge and still be usable.

Topology — who depends on whom — lives in the graph. Predicates — does ^4.1.0 admit 4.4.2, who else does this maintainer publish — live in a SQLite sidecar.

That split is why "would have pulled it" vs "shielded by a pin" is a number this thing can actually produce, instead of the much scarier and much less true count of everyone who merely lists the package.
